# 60 知識迭代與反思協議

定義：未來的模型如何**安全地**更新這套 harness。原則是「事實層開放、規則層保守、制度層鎖死」——弱模型改事實很可靠，改規則容易越改越鬆。

## 1. 檔案權限分級

| 級別 | 檔案 | 模型可否自行更新 |
|---|---|---|
| 🟢 自由更新 | `lessons.md`（只准**追加**，不准刪改舊條目）；`10-project-map.md` 的事實修正（行號漂移、新增檔案、行數表） | 可，更新後在回報中提一句即可 |
| 🟡 先改後報 | `40-delegation-templates.md` 的措辭微調；`50-deploy-verify.md` 的指令細節（URL、參數變更）；CLAUDE.md「速查」區的事實 | 可，但必須在回報中**明確列出改了哪幾行、為什麼** |
| 🔴 先問後改 | CLAUDE.md 三條鐵律；`20` 的門檻數值（失敗次數、重試上限）；`30` 的任何判準；`.claude/settings.json`、hooks；權限分級本表 | **必須先徵得使用者同意**，未同意前照舊規則執行 |
| ⛔ 唯讀 | `00-diagnosis.md`、`70-handover.md`（歷史文件） | 不可改內文；要補充就在文末加「後記（日期）」區塊 |

**方向性鐵律**：任何人（包括 Opus）不得以「效率」為由**放寬** 🔴 級規則（提高整檔讀上限、跳過隔離驗證、降低熔斷門檻）。發現規則確實太緊 → 帶著具體案例問使用者。收緊規則同樣要問（避免制度膨脹到沒人讀）。

## 2. 踩坑紀錄格式（lessons.md）

觸發時機：任何「浪費超過 3 個工具呼叫的錯誤假設」或「驗收 REJECT 的根因」都要記。格式（每條 ≤8 行）：

```
## L{編號} {日期} {一句話標題}
情境：當時在做什麼
錯誤：實際發生什麼（含關鍵錯誤訊息原文）
根因：真正的原因（不是表象）
之後怎麼做：可執行的具體指示（一條測試就能驗證的那種）
波及：需要同步更新的 harness 檔（無則寫「無」）
```

**正例**：`根因：GAS 未重新部署，curl 打到舊版。之後怎麼做：任何 Code.gs 驗證前先跑 50 號檔 §3 版本確認。波及：無（50 號檔已涵蓋）。`
**反例**：`根因：不小心弄錯了。之後怎麼做：更小心。`——沒有可執行判準的紀錄是垃圾，禁止寫入。

## 3. auto-memory 與 harness 的分工

- **auto-memory**（`~/.claude/projects/.../memory/`）：進行中工作的狀態、使用者偏好、還沒收斂的觀察。特性：不進版控、會被壓縮、可能過時。
- **harness**（本目錄，進 git）：已驗證的長期事實與規則。
- **升格規則**：一個知識若在 ≥2 個 session 都被用到、且可被驗證 → 從 memory 升格寫入 `10-project-map.md` 或 `lessons.md`，memory 裡改成一行指標。兩邊內容衝突時，**以 harness 為準**，並修正 memory。

## 4. 精簡觸發條件（防制度膨脹）

滿足任一條就要做精簡（🔴 級動作，先問使用者）：
- `lessons.md` 超過 **15 條**或 **150 行**。
- 任何單一 harness 檔超過 **250 行**。
- 出現 3 條以上 lessons 指向同一根因。

精簡方法：把同根因的多條 lessons 抽象成 1 條規則，寫入 `30-judgment-matrix.md` 第 4 節或 `10-project-map.md`；原始條目移到 `lessons-archive.md`（不刪除，保留歷史）。精簡工作建議由 Opus 級模型執行。

## 5. 更新 harness 前的自我檢查（依序執行）

1. 這個改動屬於哪一級？🔴/⛔ 級 → 先停，問使用者。
2. 我要寫入的「事實」驗證過了嗎？（Grep/實測過，不是推測）
3. 新內容有沒有跟其他 harness 檔矛盾？（Grep 關鍵詞掃一遍 harness 目錄）
4. 改完 `git diff` 確認只動了預期的行，並在回報中告知。
5. 引用的檔案路徑/函式名是否存在？（引用不存在的東西＝給未來模型埋雷）
