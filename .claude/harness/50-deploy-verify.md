# 50 部署與驗證 SOP

核心原則：**沒過「版本確認」的驗證一律無效，不得寫進任何回報。**「curl 有回應」不等於「改動已生效」。

## 1. 部署鏈全圖（誰改的、誰部署、怎麼確認生效）

| 改了什麼 | 生效方式 | 誰負責 | 版本確認方法 |
|---|---|---|---|
| 前端檔（*.html / *.js / *.css） | `git push origin main` → GitHub Pages ~1 分鐘重建 | 模型可做（push 前先告知使用者） | §2 指紋比對 |
| Code.gs | 使用者貼進 GAS 編輯器 →「部署 > 管理部署作業 > 編輯 > 新版本」（**必須編輯現有部署，不可新增部署**，否則網址會變、全站斷線） | **只有使用者能做** | §3 |
| 試算表結構（加欄/改表頭/加分頁） | 使用者手動操作試算表 | **只有使用者能做** | §4 |
| 試算表資料 | 後台操作或使用者直接編輯 | 使用者 | 重新 fetch 端點確認 |

**前置鐵律（工作分支未合併＝尚未上線）**：在工作分支（`claude/*`）上 push 只是備份到那條分支，**不等於上線**。GitHub Pages 吃 **main**，所以 `images/` 圖片與前端檔停在分支時，github.io 網址一律 404；GitHub 上 main 的 Code.gs 也還是舊的，使用者照「repo 最新 Code.gs」貼進 Apps Script 會貼到舊版。**交付含 images/ 或 Code.gs 的改動時，先在回報中點明「要先合併進 main 才會生效」，前置沒做完不得叫使用者部署或跑 GAS 函式**（見 lessons L4）。另注意：Apps Script 那份 Code.gs 永遠不會自動同步 GitHub，一定要人手貼。

## 2. 前端驗證（GitHub Pages）

1. push 完成後等 60–90 秒（背景執行 push——GCM 憑證互動的關係，前景跑會卡住）。
2. 取本地指紋：`git rev-parse --short HEAD`，並記下這次 diff 裡一段**唯一存在於新版**的字串（例：新函式名）。
3. 帶 cache-buster 抓線上檔並找指紋字串：
   `curl -s "https://dondon0813.github.io/calender/【檔名】?cb=【short-hash】" | grep -c "【指紋字串】"`
   - 回 ≥1 → 版本確認通過，才可以開始功能驗證。
   - 回 0 → 還是舊版：再等 60 秒重試，最多 3 次；3 次都失敗 → 檢查 push 是否真的成功（`git log origin/main -1`），仍異常則熔斷回報。
4. 功能驗證：能用 Browser 工具就實際打開頁面看渲染結果；不能就 curl 抓 HTML 檢查關鍵 DOM。改了 admin.js/memo.js 的話，確認 admin.html 的 `?v=` 已 +1（否則使用者瀏覽器會繼續用舊快取）。

## 3. 後端驗證（Code.gs）——本專案最大的假結論來源

**驗證前必問**：向使用者確認「Code.gs 已重新部署了嗎？」得到明確「是」之前，**禁止**對線上端點的行為下任何結論。（模型無法自行部署 GAS，也無法從外部查部署時間——這是物理斷點。）

**行為探針**（使用者說已部署後，仍要客觀確認）：
1. 找出這次改動在回傳資料上的可觀察差異（新欄位、新 scope、修正後的值）。
2. `curl -sL "【APPS_SCRIPT_URL】?scope=【scope】&t=$(date +%s)"`（`t=` 時戳防快取；`-L` 必帶，GAS 會 302）。
3. 回傳中找得到差異 → 版本確認通過。找不到 → 回報「線上仍是舊版或改動未達預期」，請使用者確認部署的是最新程式碼；**不要**開始改自己的程式碼（見 30 號檔 S4 反例）。
- 若這次改動不影響任何免登入端點的輸出（純後台邏輯），標注「無法從外部驗證，需使用者在後台實測」，並附使用者可照做的實測步驟。
- **curl 回 `http=000`／連不上時**：先跑 `curl -sS "$HTTPS_PROXY/__agentproxy/status"` 看 `recentRelayFailures`。若是 `connect_rejected`（gateway 403），代表這個 session 的網路政策擋掉外連（遠端環境常見，`script.google.com` 與 `dondon0813.github.io` 都可能被擋）——**這不是程式問題，立刻停止重試**，改走 L5 的 fallback：用 `git show origin/main:檔名 | grep` 確認 main 內容 → 如實回報「本 session 無法做線上驗證」→ 給使用者可照做的實測步驟。**禁止**把「程式碼已在 main」講成「線上已驗證通過」。

## 4. 試算表結構變更

鐵律順序：**①使用者先在試算表加好欄位/表頭 → ②才能執行/部署依賴新欄的 GAS 程式**。順序顛倒時 `appendRow` 會因欄數不符直接報錯中止（歷史事故，一筆都不會寫入）。
- 模型交付含結構變更的工作時，「給使用者的步驟清單」必須明確標出這個順序，並提供事後檢查法（例：跑一筆測試資料、curl 端點看新欄位有值）。
- 欄位索引（EVENT_COL 等）改動時，Grep 所有用到該索引的地方（前端 `c[21]` 這類寫法也要抓）。

## 5. 驗證等級表（什麼改動做到哪一關）

| 改動類型 | 必做 |
|---|---|
| 文案/樣式微調（單檔 <30 行） | D1–D2（見 30 號檔 §2）＋線上指紋確認 |
| 功能改動（含 JS 邏輯） | D1–D7 全套＋隔離驗收（模板 D） |
| 等價重構（樣式抽取、搬移） | 上一行全部＋**三關驗證法**（下述） |
| 動到 Code.gs | 上述對應等級＋§3 全流程 |
| 動到公開端點輸出 | 熔斷先問（30 號檔 F2）→ 改完後 diff 新舊回傳的**欄位集合**，確認沒有多吐欄位 |

**三關驗證法**（shared.css 遷移實戰驗出多筆無聲差異，不可省略第 2 關）：
1. `<body>` 之後的內容 diff 必須完全相同（結構等價）。
2. 把 CSS 變數展開回字面值後，逐條比對新舊宣告——舊宣告不得缺漏或被改值（樣式等價；歷史上這關抓到 `font-weight:700` vs `800` 這種肉眼看不出的差異）。
3. 反向檢查：共用樣式不會套到該頁原本無樣式的元素（無副作用）。

## 6. 鐵律：Code.gs 沒 push 上 main，禁止叫使用者部署

**這是前置條件，不是建議。違反＝使用者一定會部署到舊檔。**

使用者取得 Code.gs 的來源是 **GitHub 上的 repo**，不是模型的工作目錄。所以只要改動還停在「未提交」或「未 push」或「躺在分支上」，使用者照著去複製就是拿到舊版——而且 GAS 編輯器裡看不出版本，他會以為部署成功，接著兩邊一起對著錯的東西 debug。

**開口前必須通過的檢查（三個都要，缺一不可）：**

```bash
git status --porcelain Code.gs          # 必須無輸出＝已提交
git log --oneline -1 origin/main        # 記下 hash
git show origin/main:Code.gs | grep -c '<本次改動的特徵字串>'   # 必須 ≥1
```

第三條是關鍵：**不要只看「push 成功」，要直接確認遠端那份檔案裡真的有這次的改動**。特徵字串挑本次新增的常數名或註解（例如 `PR_ITEM_HEADERS`）。

順帶一提：`git push ... | tail` 會讓管線吃掉 push 的 exit code，push 被拒絕也會回報成功（2026-07-21 實際踩過）。**push 不要接管線**，或事後用 `git status -sb` 確認沒有 ahead。

**正確順序**：改動 → 語法檢查 → 獨立驗收 → **commit + push + 上述三項確認** → 才告訴使用者「可以部署了，commit 是 `<hash>`」→ 使用者部署 → 版本確認（§3）→ 才驗證功能。

反例（2026-07-21 連續發生數次）：改完 Code.gs 就跟使用者說「你要做的事：重新部署 Code.gs」，但當下改動還是本機未提交狀態。使用者去 GitHub 複製，拿到的是上一批的舊檔，部署完什麼都沒變。

## 7. 給使用者的部署待辦格式（交付時照抄）

**前提：已完成 §6 的三項確認。沒做完就不要輸出這段。**

```
【需要你操作】
1. 打開 Apps Script 編輯器 → 全選貼上 GitHub 上最新的 Code.gs（commit：<hash>）
2. 部署 > 管理部署作業 > 鉛筆(編輯) > 版本選「新版本」> 部署   ←不要按「新增部署」
3. （如有）到試算表【哪份表】的【哪個分頁】加欄位：【欄名】，放在【位置】
4. 完成後跟我說一聲，我會做線上驗證
```
