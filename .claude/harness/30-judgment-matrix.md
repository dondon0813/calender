# 30 判斷力外化矩陣

用途：把「高階直覺」變成可肉眼比對的檢核表。每條判準都有量化門檻＋正反例。規則：**符合判準就執行對應動作，不要跟判準討價還價**——弱模型對自己「這次不一樣」的感覺，錯誤率遠高於這張表。

## 1. 「方向錯了，立刻停下換路徑」的信號

滿足任一條 → 停止目前做法，回到拆解階段重新選路徑（不是在原路徑上再試一次）：

| # | 信號（量化） | 為什麼 |
|---|---|---|
| S1 | 同一個錯誤訊息出現第 2 次，而你的新嘗試只是「小改參數再跑一遍」 | 錯誤訊息沒變＝你的假設沒變＝結果不會變 |
| S2 | 為了讓一個「小修」通過，累計改動已波及 ≥3 個檔案或 >150 行 diff | 小修變大改＝當初對問題的定位錯了 |
| S3 | 你開始寫「特例處理」去繞過你不理解的行為（不知道為什麼壞，只知道加個 if 就好了） | 不理解的修復必然在別處再壞一次 |
| S4 | 驗證結果與預期不符，而你的解釋是「大概是快取／延遲／環境問題」**且沒有做版本確認** | 這是本專案假結論的頭號來源（見 50 號檔） |
| S5 | 你發現自己在修改「驗收條件」而不是修改「產出」來讓任務通過 | 移動球門＝已經迷路 |

**完美正例（S1/S4）**：curl 公開端點沒看到新欄位 → 不再重打第三次 curl，改為執行 50 號檔的版本確認 → 發現使用者尚未重新部署 GAS → 停下，把「請重新部署」列為待辦交給使用者。
**典型反例**：curl 沒看到新欄位 → 懷疑自己 JSON 解析寫錯 → 改解析邏輯 → 還是沒有 → 再加 retry → 燒掉 30 分鐘後才想到部署問題，而且已經把本來正確的解析程式改壞了。

## 2. 「任務真正完成」的量化驗收（Definition of Done）

**全部**打勾才可以對使用者說「完成」。少一項就只能說「已改完，尚待驗證/部署」：

- [ ] D1 改動已寫入檔案且 `git diff` 範圍與任務相符（沒有夾帶無關改動、沒有殘留 debug 代碼／console.log）。
- [ ] D2 語法關卡通過：JS/GAS 跑過 `node --check`；HTML 至少確認標籤配對與 `<script>` 區塊完整。
- [ ] D3 隔離驗收通過：fresh-context subagent 依 20 號檔第 5 節逐條 PASS。
- [ ] D4 對「實際生效版本」驗證通過（50 號檔的版本確認），或明確標注「待使用者部署後驗證」並附驗證步驟。
- [ ] D5 波及面檢查：Grep 過改動符號的其他使用處（例：改了 `postTask` 的參數，就要列出全部呼叫點並確認相容）。
- [ ] D6 需要使用者做的事（重新部署、試算表加欄、填資料）已寫成明確步驟清單。
- [ ] D7 新知識已依 60 號檔落檔（有踩坑→lessons.md；架構事實變了→10 號檔）。

**完美正例**：「school-list 加了開團標示。D1–D2 過；D3 驗收 agent 逐條 PASS（附行號）；D4 因 Code.gs 需重新部署，標注待部署並附 3 步驟驗證法；D5 確認 `getBrandStatus()` 另有 2 個呼叫點不受影響；D6 給了使用者 2 個待辦；D7 無新坑。」
**典型反例**：「已完成！程式碼看起來沒問題，本機測試通過。」——D2 以後全部沒做，「本機測試」對一個資料在雲端試算表的專案根本不成立。

## 3. 熔斷機制：停止自主作業，向使用者提問

滿足任一條 → **立刻停**，用「現況＋選項＋建議」格式提問。熔斷不是失敗，硬闖才是：

| # | 觸發條件 |
|---|---|
| F1 | 動作不可逆或影響線上資料：刪試算表欄位/分頁、改公開端點的輸出欄位、大量改寫試算表資料、`git push` 以外的任何發布行為 |
| F2 | 需要語意/資安判斷：某欄位旗標可否挪用到新場景、公開端點要不要多吐一個欄位、權限規則調整 |
| F3 | 品味/視覺定案：配色、文案語氣、版面取捨 → 產 2–3 個具體選項（附預覽方式）給使用者選，禁止自行定案 |
| F4 | 同一件事經 20 號檔升級路徑仍失敗（總嘗試 ≥4 次） |
| F5 | 發現 harness 文件與現實矛盾且無法自行查證（例：文件說有某函式，Grep 不到） |
| F6 | 任務範圍膨脹：實際工作量超出原始請求 2 倍以上，或發現使用者的請求建立在錯誤前提上 |

**完美正例（F2）**：「要在開團列顯示品牌圖，有兩條路：A. 沿用 brandThumbs 端點（不動後端，但只有填了小圖的品牌有圖）；B. 讓 public 端點多吐品牌圖片欄（要動 Code.gs 且擴大公開面）。我建議 A，因為不擴大公開資料面。你選哪個？」
**典型反例**：覺得 B 比較完整就直接改了 Code.gs 把 M 欄吐進公開端點——這正是 00 號檔誠實條款說的「語意設計決策」，弱模型自行定案的錯誤率不可接受，而且錯了就是資料外洩。

## 4. 本專案特有的判斷陷阱（歷史上真的踩過）

1. repo 拼字是 **calender**——拼成 calendar 的 URL 全部 404，不要「好心」改正拼字。
2. 兩份試算表：前台行事曆表（18DfV9…）≠ 後台私人表。討論「試算表」時先確認是哪份。
3. 「延長時間」欄位曾被存成 1900 年日期（git log 23ccd45 前後）——處理日期欄位時，寫入前先檢查年份合理性。
4. 試算表要先加欄，GAS 函式才能跑（appendRow 欄數不符直接中止，一筆都不會寫入）。
5. `showInRecipe` 旗標語意是「顯示於食材食譜頁」，**不可挪用**當其他頁面的顯示開關（brandThumbs 的閘門是「有填去背小圖」，就是為了不挪用它）。
6. 品牌名比對必須走 `normalizeBrandKey()`（小寫＋去空格），否則 `B21pro` 對不到「B21 Pro」。
7. 圖片破圖優先懷疑：絕對網址＋副檔名不符＋onerror 換 emoji 掩蓋問題（見 10 號檔 §6），不要先懷疑渲染邏輯。
