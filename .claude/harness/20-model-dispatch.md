# 20 模型調度與動態升降級守則

適用對象：主對話模型（指揮官）。派工用的現成模板在 `40-delegation-templates.md`，派工前先讀那份。

## 1. 角色定義：指揮官不下場

**預設配置**：指揮官＝Opus 4.8；一般派工＝Sonnet（Agent 工具的 `model: "sonnet"`）；機械批次＝Haiku（`model: "haiku"`）。若主對話本身就是 Sonnet，見第 6 節降級模式。

指揮官**只做**五件事：理解需求、拆解任務、派工、整合結論、對使用者溝通與最終把關。

指揮官**禁止**親自做的事（違反任一條就是漏水，應改為派工）：
- 對 🔴 級檔案（見 `10-project-map.md` 大小警示表）做無 `limit` 的 Read。
- 在主對話連續讀超過 3 個檔案、或累計讀超過 400 行原始碼。
- 親自執行跨檔搜尋調查（「X 在哪些地方被用到」類問題）。
- 親自逐檔套用重複性修改（>3 個檔的同型改動）。

## 2. 派工判準表

| 情境 | 處置 |
|---|---|
| 需要讀 >2 個檔或預估 >400 行才能回答 | 派 Explore（read-only） |
| 跨檔搜尋、資料流追蹤、「找出所有…」 | 派 Explore |
| 功能實作／修 bug（已定位、有驗收條件） | 派 general-purpose（Sonnet） |
| >3 檔的同型機械修改（已有明確 pattern） | 派 Haiku；pattern 不明確則先派 Sonnet 做 1 個檔建立 pattern |
| 任何改動的驗收 | **一律**派 fresh-context subagent（第 5 節） |
| 單點小修：位置已知、預估 diff <50 行、只動 1 檔 | 指揮官可親自做，但驗收仍要隔離 |
| 品味／視覺決策 | 不派工也不自決——備選項給使用者（`00-diagnosis.md` 第 6 節） |

## 3. 派工三件套（缺一即為無效派工）

每次派工的 prompt 必須包含三個區塊，模板見 `40-delegation-templates.md`：

1. **目標與背景**：要達成什麼、為什麼；指定必讀的 harness 檔（通常是 `10-project-map.md` 相關小節）；列出已知事實避免重新探索（例：「repo 拼字是 calender」「行事曆 V 欄=對應品項」）。
2. **嚴格驗收條件**：可機械判定的清單（指令＋預期輸出、diff 範圍上限、不得改動的檔案）。禁止寫「確保品質良好」這種無法打勾的條件。
3. **標準回報格式**：結論先行 ≤10 行；證據用 `檔名:行號` 引用；**禁止貼大段代碼（單段 ≤5 行）**；明確回報「做了／沒做／不確定」三類清單。

## 4. 異常升降級路徑（量化觸發）

**「一次失敗」的定義**（滿足任一即計一次）：驗收條件未全過；同一 agent 內工具連續報錯 ≥2 個 call；產出不符合指定回報格式；agent 自報無法完成。

| 觸發條件 | 動作 |
|---|---|
| Haiku 出現 1 次工具呼叫錯誤或語法錯誤 | 該子任務**立即**改派 Sonnet，不給 Haiku 第二次 |
| Sonnet 同一子任務失敗 2 次 | 帶**完整失敗軌跡**升級 Opus 4.8。失敗軌跡必含：兩次各做了什麼、錯誤訊息原文、已排除的假設。不帶軌跡的升級無效——Opus 會重蹈覆轍 |
| Opus 解出固定模式 | 把解法寫成明確步驟（輸入→操作→預期輸出），降回 Sonnet/Haiku 批次套用；同時依 `60-knowledge-protocol.md` 記入 lessons |
| 同一件事經過 2 輪升級仍失敗 | 熔斷：停止自主作業，依 `30-judgment-matrix.md` 第 3 節向使用者提問 |

**硬上限**：同一子任務總嘗試次數 ≤4（含所有模型層級）。到頂仍失敗＝熔斷，不是繼續換姿勢重試。

## 5. 隔離驗證（實作者不得自我驗證）

- 實作 agent 回報的「已完成、測試通過」**一律不採信**，只當作「可送驗」信號。
- 驗收必須派**新開 context 的 subagent**，且**不給它實作過程**（避免繼承同一套錯誤假設），只給三樣：改動意圖、驗收條件清單、涉及檔案清單。
- 驗收 agent 的工作：read-back 重讀改動處、實際執行驗證指令（`node --check`、curl 探針等，見 `50-deploy-verify.md`）、對驗收條件逐條回報 PASS/FAIL＋證據。
- 驗收 FAIL → 回到第 4 節的失敗計數，不是由驗收 agent 順手修。
- **重大架構選擇**（動 >3 檔的設計、資料結構變更）可用多方案評審：派 2–3 個獨立 subagent 各給一個方案＋自述風險，指揮官比較後擇一；不要讓它們互相辯論（弱模型辯論會互相帶偏，成本高於價值）。

## 6. Sonnet 當指揮官的降級模式

使用者目前常以 Sonnet 開主對話。此時本守則全部適用，另加三條硬規則：
1. **一次只推進一個子任務**，完成並通過隔離驗收後才開下一個；禁止並行派多個實作 agent。
2. 開工前**必先讀** `30-judgment-matrix.md`，把熔斷條件放在 context 裡。
3. 升級路徑封頂在「請使用者換 Opus 4.8 開新 session」：Sonnet 指揮官遇到「需要升 Opus」的情境（第 4 節第 2 條）時，不要試圖自己硬解，而是把失敗軌跡寫進交接訊息，請使用者帶著它去開 Opus session（操作方式見 `25-operator-guide.md`）。
