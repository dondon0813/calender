撰寫：Fable 5，2026-07-19。收件人：未來在此環境工作的所有模型，以及 Shirley。本檔為 ⛔ 唯讀歷史文件，補充請寫「後記」。

## 1. 三件沒被問到、但最關鍵的事

**其一：這個專案最大的風險不是程式壞掉，是資料外洩，而且防線只有紀律。**
後台試算表有員工密碼雜湊與 session token；GAS 的 Script Properties 裡有一把**能寫 GitHub repo 的 token**（圖片庫功能靠它代理 GitHub API）。這些東西目前都安全，但安全的前提是三條紀律：token 與 pepper 永遠只住在 GAS 端、公開端點永遠只吐白名單欄位、任何「把它搬到前端比較方便」的想法一律熔斷。未來某個模型一定會在某次除錯時產生「直接在前端呼叫 GitHub API 就能繞過這個 bug」的念頭——那就是事故的開端。另外，依 memory 記載，行事曆表改私人的最後一步（使用者驗證後切私人）可能尚未完成；若日後發現 gviz 直讀壞掉，那是**預期行為**（前端已改走 GAS），不要「修好它」把表改回公開。

**其二：admin.js 是一顆會繼續長大的單體，抵抗重寫的誘惑。**
5700 行、以註解分隔線分區的單檔，每個弱模型看到都會想提議「模組化重構」。不要做。理由：沒有測試防護網、沒有建置工具鏈、使用者無法承擔回歸風險，而現有結構靠 10 號檔地圖已經可維護。正確的方向是 memo.js 模式——**新功能寫成獨立 js 檔掛進 admin.html**，舊代碼只動不搬。什麼時候才值得大重構？當使用者主動抱怨維護困難，且願意投入完整回歸驗證的時候，而不是模型覺得代碼醜的時候。

**其三：這套制度最值錢的一次性升級，是給 doGet 加一個 version 欄位。**
目前後端驗證要靠「問使用者＋行為探針」（50 號檔 §3），因為模型無法得知 GAS 部署的是哪版。只要在 Code.gs 的 doGet 回傳裡加一個常數欄位（例：`version: "2026-07-19-a"`，每次改動時手動 +1），部署驗證就從「通靈」變成「讀數字」，50 號檔 §3 可以整段簡化。這是小改動大回報，但因為它動 Code.gs 且需要使用者配合部署習慣（每次改動記得改版本字串），我沒有擅自實作。未來哪個 session 做後端改動時，順路提案給使用者。

## 2. 制度在弱模型長期運作下的退化模式與預防

| 退化模式 | 長什麼樣子 | 預防機制 |
|---|---|---|
| **規則稀釋** | 模型更新文件時把硬規則改寫成軟建議（「禁止」變「盡量避免」） | 60 號檔權限分級：規則層 🔴 先問後改；改動必附 git diff |
| **儀式化** | 表面照模板派工，但驗收條件填成「確保功能正常」這種不可判定的話 | 模板明文禁止；使用者抽查法在 25 號檔 §5（看有沒有 D1–D7 報告） |
| **地圖腐化** | 行號漂移沒人修 → 模型開始不信任地圖 → 回到整檔讀的老路 | 地圖以 Grep 錨點為主、行號為輔；🟢 級開放隨手修正；hook 物理擋住老路 |
| **文件膨脹** | lessons 越記越多沒人讀，harness 變成沒人載入的裝飾品 | 60 號檔 §4 量化精簡觸發（15 條/150 行/250 行） |
| **hook 被摩擦磨掉** | hook 誤擋幾次正當操作 → 使用者乾脆停用 → 防線消失 | hook 範圍窄（只擋 >50KB 無 limit 的 Read）、錯誤訊息教正確做法；真誤擋就依 🔴 流程調參數，不要停用 |
| **產品漂移** | Claude Code 改版後 hook 語法/工具名失效，文件引用落空 | 30 號檔 F5：發現引用不存在 → 熔斷回報並修文件，不硬套 |

總原則：這套制度的敵人不是弱模型的能力，是**沒有阻力的小偏移累積**。所以關鍵防線都做成物理的（hook、權限分級、模板必填欄），不依賴模型自覺。
